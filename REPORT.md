# Разработка проекта Library Booking

## Общая картина

Проект постепенно собирается вокруг сервиса бронирования книг в библиотеках. Работа разделена на этапы: сначала подготовлен backend-фундамент, затем добавлены пользователи и авторизация, каталог библиотек и книг, бронирование, а после этого интерфейсы для работы с каталогом.

Архитектура строится на NestJS, TypeORM и PostgreSQL на backend. Frontend использует React, TypeScript, Vite, Redux Toolkit и React Router. Общение между частями приложения идёт через REST API.

---

# День 1. Основа backend и пользователи

## 1. Подготовка приложения

Сначала настроен запуск NestJS-приложения:

- добавлен общий префикс API `/api`;
- подключён Helmet для базовых HTTP-заголовков безопасности;
- настроен глобальный `ValidationPipe`, который проверяет входные данные и преобразует их к нужным типам;
- подключён `ConfigModule` для чтения настроек из `.env`;
- добавлена проверка обязательных переменных окружения при запуске;
- настроено подключение TypeORM к PostgreSQL;
- добавлен `GET /api/health`, который возвращает статус приложения.

Локальные настройки вынесены в `.env`. Файл не должен попадать в Git.

## 2. Общие инструменты

Созданы небольшие общие элементы, которые используются в разных модулях:

- `ID` — единый тип идентификатора;
- `escapeLike()` — экранирование специальных символов в поисковых запросах `ILIKE`;
- `PaginationQueryDto` — общие параметры пагинации `offset` и `limit` с ограничениями и значениями по умолчанию.

## 3. Работа с пользователями

Создан `UsersModule`.

Сущность `User` описывает пользователя в базе данных: email, хеш пароля, имя, телефон, роль и даты создания/обновления.

Внутри модуля реализованы два сервиса:

- `UsersService` создаёт пользователей и ищет их по ID, email или списку параметров;
- `PasswordService` хеширует пароли через bcrypt и сравнивает введённый пароль с сохранённым хешем.

Поиск пользователей поддерживает фильтрацию по email, имени и телефону. Для текстовых полей используется `ILIKE`, а результаты можно получать постранично.

## 4. Начальные пользователи

Добавлен `SeedService`. При запуске приложения он проверяет наличие пользователей с данными из переменных `SEED_*` и при необходимости создаёт:

- администратора;
- менеджера.

Пароли сразу хешируются. Если пользователь с таким email уже есть, повторно он не создаётся.

## Как всё связано

`AppModule` подключает `DatabaseModule`. Тот настраивает соединение с PostgreSQL, регистрирует `UsersModule` и запускает `SeedService`.

При старте приложения сначала загружается конфигурация, затем устанавливается соединение с базой. После этого сервис начальных данных проверяет наличие администратора и менеджера.

# День 2. Авторизация, маршрутизация и пользователи на frontend

Backend авторизации и управления пользователями был подготовлен отдельно. На этом этапе реализована клиентская часть, которая использует готовые API-методы.

## 1. Авторизация

В Redux добавлен `authSlice` с операциями:

- `login` — вход;
- `register` — регистрация;
- `logout` — выход;
- `fetchMe` — получение текущего пользователя.

При запуске приложения выполняется `fetchMe`. Пока сервер проверяет сессию, показывается полноэкранный индикатор загрузки. Благодаря этому приложение не успевает ошибочно перенаправить пользователя до завершения проверки.

Сессия хранится на сервере и передаётся через cookie. Пароли и данные сессии не сохраняются в Redux или браузерном хранилище.

## 2. Вход и регистрация

Вместо заглушек созданы полноценные страницы:

- `LoginPage` — форма входа с проверкой полей и понятным сообщением при неверной паре email/пароль;
- `RegisterPage` — форма регистрации с проверкой email, пароля, имени и телефона.

После успешной регистрации пользователь переходит на страницу входа. Автоматический вход не выполняется, поскольку backend отдельно его не запускает.

Если пользователь открыл закрытую страницу до входа, приложение запоминает исходный адрес и возвращает его туда после авторизации.

## 3. Защита страниц и навигация

Добавлены компоненты для контроля доступа:

- `GuestRoute` — страницы, доступные только гостям;
- `ProtectedRoute` — страницы для авторизованных пользователей;
- `RoleRoute` — страницы, доступные только определённым ролям.

Маршруты распределены по ролям: клиент, менеджер и администратор видят разные разделы приложения. При попытке открыть чужой раздел пользователь перенаправляется на главную страницу.

В `Navbar` добавлено меню, которое меняется в зависимости от роли. Для авторизованного пользователя отображаются его имя и кнопка выхода.

## 4. Управление пользователями

Для администратора создана страница `/admin/users`:

- таблица пользователей;
- фильтры по email, имени и телефону;
- постраничная навигация;
- форма создания пользователя с выбором роли.

Для менеджера создана страница `/manager/users`. Она показывает список пользователей и поддерживает те же фильтры и пагинацию, но не предоставляет административных действий.

Повторяющиеся элементы вынесены в общие компоненты: фильтры, таблицу, форму создания, индикатор загрузки, сообщение об ошибке и пагинацию.

# День 3. Каталог библиотек и книг

Работа над каталогом разделена на backend и frontend.

## 1. Backend: сущности и правила каталога

Созданы сущности `Library` и `Book`.

У библиотеки есть название, адрес и описание. Книга связана с библиотекой и хранит название, автора, год, описание, путь к обложке и сведения о количестве экземпляров.

Для книг предусмотрены ограничения на количество экземпляров: общее количество не может быть меньше одного, а доступное количество должно находиться в диапазоне от нуля до общего количества.

Добавлены индексы для основных полей поиска.

## 2. API каталога

Реализованы публичные запросы:

- получить список библиотек;
- получить библиотеку по ID;
- искать книги с фильтрами по библиотеке, автору, названию и доступности;
- получить книгу по ID.

Для административной роли добавлены операции создания, редактирования и удаления библиотек и книг.

При создании и редактировании книги можно загрузить обложку. Принимаются JPEG, PNG и WebP размером до 2 МБ. Файлам назначаются собственные имена, а изображения доступны по пути `/uploads/...`.

При замене обложки старый файл удаляется. При удалении книги удаляется её обложка, а при удалении библиотеки обложки её книг очищаются вместе с каталогом.

При изменении общего количества экземпляров пересчитывается доступное количество с учётом уже выданных книг.

## 3. Подготовка к модулю аренды

На этом этапе в модуле книг появилась проверка, которая должна запрещать удаление книги или библиотеки при активных арендах.

Поскольку сам модуль аренды ещё не был готов, сначала использовалась временная реализация `NoActiveRentalsChecker`. Она позволила заранее определить интерфейс взаимодействия между модулями. На следующем этапе заглушка была заменена реальным сервисом.

## 4. Демо-данные

Добавлен скрипт `seed:demo`, который создаёт три библиотеки и пятнадцать книг. Повторный запуск не создаёт дубликаты.

## 5. Frontend: поиск книг

На главной странице вместо заглушки появился каталог книг.

Добавлены API-клиенты для библиотек и книг, а также Redux-срезы для загрузки данных. Список библиотек используется в фильтре, а книги загружаются с учётом параметров поиска.

Фильтры позволяют выбрать библиотеку, указать автора и название, а также оставить только доступные книги.

Результаты выводятся карточками. В карточке есть обложка, название, автор, библиотека и информация о доступности экземпляров. Если обложки нет или изображение не загрузилось, показывается плейсхолдер.

Добавлена пагинация. Чтобы понять, есть ли следующая страница, frontend запрашивает на одну книгу больше отображаемого лимита.

Также предусмотрена защита от гонки запросов: если пользователь быстро меняет фильтры, устаревший ответ не перезаписывает более свежие результаты.

# День 4. Бронирование книг

## 1. Backend: модель аренды

Создана сущность `BookRental`, которая связывает пользователя, книгу и библиотеку. Запись хранит даты начала и окончания, статус бронирования и даты создания/обновления.

У бронирования есть четыре статуса:

- `reserved` — бронь создана;
- `active` — книга выдана;
- `completed` — аренда завершена;
- `cancelled` — бронь отменена.

## 2. Правила бронирования

Клиент может создать бронь, посмотреть свои бронирования и отменить бронь со статусом `reserved`.

При создании проверяются даты, существование книги и соответствие библиотеки выбранной книге. Нельзя создать бронь на прошедшие даты, на период больше установленного срока или на даты, пересекающиеся с другой активной бронью той же книги.

Менеджер может просматривать бронирования, фильтровать их и менять статусы.

Разрешены только определённые переходы:

- `reserved → active`;
- `reserved → cancelled`;
- `active → completed`;
- `active → cancelled`.

Клиент может отменить только собственную бронь со статусом `reserved`. Менеджер может выполнять предусмотренные переходы статусов. Недопустимые переходы отклоняются.

## 3. Учёт экземпляров

Создание брони со статусом `reserved` не уменьшает количество доступных экземпляров.

Когда менеджер переводит бронь в `active`, доступное количество уменьшается на один. При завершении или отмене активной аренды экземпляр возвращается в доступные.

Поле `isAvailable` обновляется на основании `availableCopies`.

## 4. Защита от одновременного бронирования

Отдельно обработан случай, когда несколько клиентов пытаются забронировать последний экземпляр на один и тот же период.

Создание брони выполняется внутри транзакции с блокировкой строки книги (`FOR UPDATE`). Поэтому запросы обрабатываются последовательно: один может успешно создать бронь, а следующий получает конфликт, если экземпляров на этот период уже не осталось.

Это защищает от ситуации, когда два клиента одновременно получают подтверждение на один и тот же последний экземпляр.

## 5. Связь с каталогом

Вместо временного `NoActiveRentalsChecker` подключён настоящий `RentalsService`.

Теперь удаление книги или библиотеки запрещено, если у них есть бронирования со статусом `reserved` или `active`. В таком случае API возвращает `409 Conflict`.

После отмены или завершения бронирований удаление снова возможно. При удалении книги или библиотеки связанная история аренд удаляется каскадно согласно принятому решению по внешним ключам.

## 6. API аренды

Для клиента реализованы:

- `POST /api/client/rentals` — создать бронь;
- `GET /api/client/rentals` — получить свои брони;
- `DELETE /api/client/rentals/:id` — отменить свою бронь.

Для менеджера:

- `GET /api/manager/rentals` — получить список броней с фильтрами;
- `PATCH /api/manager/rentals/:id/status` — изменить статус.

В ответах со списками дополнительно возвращается краткая информация о книге и библиотеке. В менеджерском списке также есть данные пользователя.

## 7. Frontend: управление каталогом и страница книги

На frontend добавлены административные страницы:

- `/admin/libraries` — список библиотек, создание, редактирование и удаление;
- `/admin/books` — список книг, создание, редактирование и удаление.

Удаление сопровождается модальным окном подтверждения. Ошибки API, включая `409 Conflict`, показываются пользователю.

В форме книги можно выбрать библиотеку и загрузить обложку. При редактировании показывается текущая обложка и предварительный просмотр нового изображения. Если новый файл не выбран, существующая обложка остаётся без изменений.

Также реализована публичная страница `/books/:id` с подробной информацией о книге: обложкой, названием, автором, годом, описанием, библиотекой и количеством доступных экземпляров.

Для подтверждения удаления создан общий компонент `ConfirmModal`.

## 8. Дополнительный блок на главной странице

На главную страницу добавлен компонент `BookSwiper` на базе Swiper.

Он показывает подборку книг в виде слайдера. Можно передать конкретные ID книг или получить случайную подборку. Поддерживаются заголовок блока и автопрокрутка.

Слайдер адаптируется к ширине экрана, поддерживает навигационные стрелки, точки и управление с клавиатуры. Загрузка книг выполняется через существующий API, а порядок переданных ID сохраняется.

# Итоговая структура проекта

К этому этапу в приложении сформированы основные функциональные области:

- **Пользователи и авторизация:** регистрация, вход, выход, получение текущего пользователя, роли и управление пользователями.
- **Каталог:** библиотеки, книги, поиск, фильтры, обложки и подробная страница книги.
- **Бронирование:** создание и отмена броней, управление статусами, проверка доступности экземпляров и защита от конфликтующих бронирований.
- **Административная часть:** управление библиотеками, книгами и пользователями.
- **Общий интерфейс:** навигация по ролям, загрузка и обработка ошибок, пагинация, модальные подтверждения и слайдер подборки книг.

Работа шла от базовой инфраструктуры к отдельным предметным модулям. Сначала были подготовлены конфигурация, база данных и пользователи. Затем frontend получил авторизацию и ролевую навигацию. После этого появился каталог, а модуль бронирования связал пользователей, книги и библиотеки общими бизнес-правилами. В конце административные сценарии каталога получили полноценный интерфейс.

Замечания и несоответствия backend
1. Списки без total: GET /client/rentals и GET /manager/rentals возвращают просто массив — пагинация сделана принятым в проекте приёмом «limit + 1 = есть следующая страница». Как и у GET /common/books раньше, точный счётчик «Всего: N» на бэке сделать нельзя без изменения ответа.
2. Фильтр менеджера по пользователю — только точный userId, поиск по имени/email в API отсутствует. Сделал select из /manager/users, но API ограничивает limit ≤ 100, поэтому при >100 пользователей в списке будут не все (список библиотек — та же история).
3. GET /client/rentals поддерживает фильтр status — в UI не используется (в задаче не требовался).
4. Навигация: в UserMenu и Navbar пунктов «Мои брони»/«Аренды» нет — по условию меню не трогал; страница клиента открывается редиректом после бронирования и по прямому URL /my/rentals. Если нужно — добавить пункты в меню отдельным решением.
